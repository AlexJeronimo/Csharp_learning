Щодо того, що пишеться зліва від назви — у C# ці слова називаються модифікаторами. 
Вони завжди йдуть у суворому порядку:
`[Доступ] [Поведінка/Специфіка] [Тип даних] НАЗВА`
Розберемо кожну групу.
1. Модифікатори доступу (Хто бачить цю сутність)
Це "рівні приватності". Вони визначають, звідки можна звернутися до класу, методу чи змінної:
`private` (приватний) — видно тільки всередині цього ж класу. Для полів це стандарт (інкапсуляція).
`public` (публічний) — видно звідусіль (з інших класів, файлів, проєктів).
`protected` (захищений) — видно всередині цього класу + у всіх його похідних класах-нащадках (наприклад, батько Creature і нащадок Player).
`internal` (внутрішній) — видно з будь-якого місця, але тільки в межах поточного проєкту (сборки/assembly).
2. Модифікатори поведінки (Як це працює)Це додаткові інструкції для компілятора, які змінюють логіку роботи:
Для класів:
`abstract` — клас-заготовка. З нього не можна створити об'єкт через new Creature(). Використовується тільки як батько для наслідування.
`sealed` (запечатаний) — забороняє наслідування. Від цього класу не можна створити похідні класи (наприклад, `public sealed class Player`).
`static` — клас-утiлiта. Не потребує створення об'єктів через new. Всі його елементи теж мають бути static (приклад: `Math.Sqrt()`).
Для методів та властивостей:
`static` — належить самому класу, а не конкретному об'єкту. Викликається як ClassName.Method().
`virtual` — метод має дефолтний код, але нащадки можуть його переписати за допомогою override.
`override` — вказує, що цей метод перевизначає virtual або abstract метод батьківського класу.abstract — метод без коду. Оголошує тільки назву та параметри. Змушує нащадків написати override.
Для змінних (полів):
`readonly` — значення можна задати тільки під час оголошення або в конструкторі. Після цього змінити його неможливо.
`const` — константа. Значення має бути відоме ще на етапі написання коду (наприклад, const double Pi = 3.14;). Змінити її взагалі неможливо.
3. Тип даних або повернуте значенняВказує, з якими саме даними працює змінна або що повертає метод:Для змінних: 
int, string, bool, Creature, `List<string>` тощо.
Для методів:
Назва типу (int, string), якщо метод повертає результат після виконання.
void — якщо метод просто робить дію і нічого не повертає (наприклад, друкує в консоль або змінює стан).
Шпаргалка на реальному прикладіПодивіться, як це збирається в один рядок зліва направо:
 [Доступ]  [Поведінка]  [Тип]   [Назва]
 private    readonly    string   id;

//  [Доступ]  [Поведінка]  [Повертає]  [Назва]    [Параметри]
    ```
    public     virtual      void       TakeDamage (int amount)
    {
        // ...
    }
    ```

//  [Доступ]  [Поведінка]  [Повертає]  [Назва]
    `public     override     string     ToString() => Name;`

//  [Доступ]  [Поведінка]  [Класи]
    `public     abstract     class      Creature`
Якщо читати ці слова зліва направо, ви завжди будете чітко розуміти: хто має доступ -> як воно поводиться -> який тип даних там лежить.

1. Інтерфейси vs Базовий клас (Класове наслідування)
Головне правило розмежування:

Класове наслідування (class Parent) — це зв'язок «ЧИМ Є об'єкт» (Is-A). Воно передає і структуру, і готову реалізацію (код).

Інтерфейс (interface I...) — це контракт або «ЩО ВМІЄ робити об'єкт» (Can-Do). Він не містить даних (полів), а лише каже: «Хто мене підпише, той зобов'язаний реалізувати такі методи».

Чому Creature краще зробити абстрактним класом, а не інтерфейсом?
Якщо ви зробите ICreature інтерфейсом, ви не зможете зберегти в ньому приватні поля (health, damage, id) чи готову логіку методів TakeDamage і Heal. Вам доведеться заново писати одні й ті самі поля і код в кожному класі (Player, Goblin, Dragon).

Для загальних характеристик і готового коду використовують абстрактний клас:


// БАЗОВИЙ КЛАС: Тут лежить ГОТОВИЙ код, який спільний для всіх
```C#
public abstract class Creature
{
    public string Name { get; set; }
    public int Health { get; protected set; }

    public void Heal(int amount) => Health += amount; // Готовий метод, однаковий для всіх
    public abstract void Attack(); // Абстрактний метод: кожен розробляє свою атаку
}
```
Для чого тоді потрібні інтерфейси?
Інтерфейси ідеально підходять для додаткових можливостей, які є тільки у деяких істот, або для об'єктів з різних родин.

Уявіть, що у вас є:

Player (Гравець)

Goblin (Ворог-істота)

DestructibleBarrel (Дерев'яна бочка, яка не є істотою, але її можна розбити)

MagicScroll (Магічний сувій, який можна використати для лікування)

Бочка — це не Creature (у неї немає рівня, імені чи мани), але їй теж можна завдати шкоди.

Ось де вистрілюють інтерфейси:


// Контракт: все, що реалізує цей інтерфейс, можна атакувати
```C#
public interface IDamageable
{
    int Health { get; }
    void TakeDamage(int amount);
}

// Контракт: все, що реалізує цей інтерфейс, вміє лікувати
public interface IHealable
{
    void Heal(int amount);
}
```

// Бочка НЕ істота, але її можна ламати!
```
public class DestructibleBarrel : IDamageable
{
    public int Health { get; private set; } = 20;
    public void TakeDamage(int amount) => Health -= amount;
}
```

// Гравець і істота, і його можна атакувати, і лікувати
```
public class Player : Creature, IDamageable, IHealable
{
    public void TakeDamage(int amount) => Health -= amount;
}
```
Головний плюс: У грі ви можете зробити метод AttackTarget(IDamageable target). І туди можна буде передати і Гобліна, і Бочку, і Гравця, бо вони всі підтримують контракт IDamageable!

2. Як працює наслідування класів і перевизначення методів
Щодо вашого другого питання: чи потрібно завжди перевизначати методи батьківського класу?

Ні, не завжди. Це залежить від того, як ви оголосили метод у батьківському класі:

А. Звичайний метод (не можна перевизначити)
Похідний клас просто успадковує його "як є" і використовує готову логіку.

```C#
public class Creature 
{
    public void Rest() => Console.WriteLine("Відпочиває..."); 
}
```
// У Player метод Rest() працюватиме точно так само без жодного додаткового коду.
Б. virtual метод (можна перевизначити за бажанням)
Батько дає реалізацію за замовчуванням, але каже: «Якщо похідному класу це не підходить — він може переписати метод через override».

```C#
public class Creature 
{
    public virtual void TakeDamage(int damage)
    {
        Health -= damage; // Базова логіка
    }
}

public class Player : Creature
{
    // Перевизначаємо, бо у Гравця є Броня
    public override void TakeDamage(int damage)
    {
        int finalDamage = damage - Armor;
        base.TakeDamage(finalDamage); // base. викликає базову логіку батька
    }
}

public class Goblin : Creature
{
    // Гоблін НЕ перевизначає TakeDamage, він просто використовує стандартний метод батька!
}
```
В. `abstract` метод (ОБОВ'ЯЗКОВО перевизначити)
У батьківському класі немає тіла методу (немає {}). Батько лише оголошує назву, а кожен похідний клас зобов'язаний написати свою реалізацію через override.

```C#
public abstract class Creature 
{
    public abstract void MakeSound(); // Немає реалізації!
}

public class Goblin : Creature
{
    public override void MakeSound() => Console.WriteLine("Гррр!"); // ОБОВ'ЯЗКОВО!
}
```
Коротке резюме для практики
Creature зробіть abstract class — там напишіть спільні змінні (Health, Name) та методи, які однакові для всіх (Heal).

Для специфічних дій (атакувати, застосовувати магію, розбивати) створіть interface (наприклад, IAttacker, IDamageable).

Якщо метод у батька має готовий код і він підходить усім — робіть його звичайним.

Якщо код підходить більшості, але хтось має рахувати по-іншому — робіть virtual і в похідному класі пишіть override.

Якщо у кожного метод має працювати унікально і спільного коду немає — робіть abstract.
